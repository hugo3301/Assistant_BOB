# Резервирование и восстановление BOB

Задача bob-wrh.6, 15 ноября 2026. Пользователь согласовал локальные зашифрованные файлы в `D:\Assistant_BOB\work\backups`, вне Git. Бесплатно: используются существующие Worker/DO и компьютер владельца, без нового облачного хранилища. Копии всех активных участников доступны только оператору с ADMIN_SECRET; каждый файл привязан к исходному Telegram ID. В модели ИИ и Telegram копии не отправляются.

## Что сохраняется

Дела (включая закрытые), проекты/категории/рацион, настройки часового пояса и напоминаний, недельные серии и их active-флаг, идентификаторы исходных экземпляров, фильтры и исключения .ics, метаданные событий, календарные сопоставления и конфликты, статусы/dedupe отправленных напоминаний. Снимок одного пользователя снимается синхронной транзакцией SQLite; разные пользователи снимаются последовательно, общего момента всех баз нет. Лимит одного снимка: 20 000 строк суммарно / 4 MiB JSON, при превышении операция завершается ошибкой, без усечённой успешной копии.

Не сохраняются серверные ключи, пароли/токены календарей, OAuth-сеансы, согласия дополнительных AI-провайдеров, история диалога/уточнения/кнопки, задания и исходящие ответы Telegram, метрики, глобальный реестр участников и квоты ControlObject. После восстановления календарные связи сохраняются, но подключение отключено до повторного входа. Провайдеры требуют нового выбора. ControlObject и серверные secret bindings нужно сохранить отдельно; это восстановление личных данных, а не полная копия Cloudflare-аккаунта или базы Beads.

## Создание копий

Из `D:\Assistant_BOB` (Node 24+), в доверенном терминале:

```powershell
node --env-file=.env scripts/backup.mjs init-key
node --env-file=.env scripts/backup.mjs create --all
node --env-file=.env scripts/backup.mjs inspect --file work/backups/ИМЯ.bobbackup
```

`init-key` выполняется один раз: отдельный случайный 256-bit BACKUP_ENCRYPTION_KEY добавляется только в исключённый `.env`, значение не печатается, существующий ключ не заменяется. Каждый файл шифруется AES-256-GCM с новым nonce и контекстом; расшифровка проверяется до записи, запись `wx` не заменяет предыдущую копию. Потеря этого ключа делает копии невосстановимыми: нужна отдельная защищённая копия ключа в доступном владельцу хранилище паролей. Ключи не включаются в сами файлы. Файлы нельзя отправлять в публичные репозитории; расшифрованный снимок содержит личные сведения. `inspect` выводит только дату и числа.

Автоматизация Windows:

```powershell
powershell -NoProfile -File scripts/install-backup-task.ps1
Get-ScheduledTaskInfo -TaskName 'Assistant_BOB Daily Backup'
```

Ежедневно в 08:10 по часовому поясу Windows, при пропущенном запуске — после доступности компьютера. Нужны вход этого пользователя в Windows и интернет, пароль/права администратора не сохраняются. В параметрах задания только путь скрипта, не секреты. Копии автоматически не удаляются. Проверять LastTaskResult (0), дату последнего файла и свободное место. При выключенном компьютере копии не создаются. Фактический предел потери — всё после `createdAt` последней успешно проверенной копии; 24 часа достижимы только при ежедневном успешном запуске, гарантированного RPO нет. RTO зависит от восстановления аккаунта/ключей/реестра и не измерен для настоящей аварии.

## Восстановление

Только в пустое хранилище **того же** Telegram ID, в сохранённом реестре активных участников ControlObject. Рабочая непустая база (даже только с закрытыми делами или историей) не перезаписывается. Сначала проверить копию через inspect. При потере всего ControlObject сначала требуется отдельно восстановить реестр и квоты: этот инструмент их не сбрасывает и не выдаёт новым ID чужие данные.

1. С отдельного поручения владельца на время обслуживания включить `BACKUP_RESTORE_ENABLED=true` в Worker. В обычной публикации флаг отсутствует: публичные restore/resume запрещены. Не добавлять его в постоянную конфигурацию/CD. Сохранить существующие secret bindings и ControlObject.
2. Выполнить в доверенном терминале, подставив **исходный** ID и файл:

```powershell
node --env-file=.env scripts/backup.mjs restore --file work/backups/ИМЯ.bobbackup --owner ID --confirm restore-empty:ID
```

3. Восстановленное хранилище остаётся на паузе, без alarm, отправок и синхронизации. Проверить данные через служебную диагностику/снимок. Старые/claimed просроченные напоминания помечаются skipped, отправленные сохраняют sent/dedupe, future остаются pending. Сегодняшняя утренняя сводка не запускается повторно. Пауза не предназначена для продолжительного использования: сообщения, приходящие в этот период, не обрабатываются, поэтому пользователю нужно дождаться окончания обслуживания и повторить запросы.
4. Явно возобновить:

```powershell
node --env-file=.env scripts/backup.mjs resume --owner ID --confirm resume:ID
```

На resume дополнительно пропускаются уведомления, просроченные за время проверки; сводки разрешены со следующего местного дня. Alarm запускается, календари остаются выключенными до нового входа. После проверки вернуть restore-флаг в false/удалить его. Не проверять восстановление на рабочей базе.

Cloudflare дополнительно описывает [PITR за последние 30 дней](https://developers.cloudflare.com/durable-objects/api/sqlite-storage-api/#point-in-time-recovery). Этот инструмент PITR не вызывает и не утверждает, что он проверен на реальной базе. PITR может вернуть старые очереди/напоминания; применять его без отдельного плана остановки доставки нельзя.

## Проверки

Node/SQLite: AES-GCM, неверный ключ/порча, владение, версия/схема, отказ непустой базе и атомарность, проекты/серии/исключения, сохранение будущего уведомления и отсутствие повторов старого. Workerd: HTTP admin-auth, отключённое production-восстановление, снимок и восстановление в отдельный тестовый object ID с той же пользовательской привязкой, pause и отсутствие outbox. Внешние сервисы в тестах подменены; реальные дела не используются для проверки восстановления.
