## Маршрут и границы

Telegram, пользовательские базы, задания и напоминания остаются в Cloudflare. При личном выборе GigaChat Worker резервирует токены, подписывает запрос к `https://<project>.vercel.app/api/gigachat` либо соответствующему `netlify.app/api/gigachat` и ждёт ограниченный ответ. На выбранном хостинге (Vercel или Netlify) только Node-функция и ключ GigaChat; секреты Telegram, Cloudflare, Google/Яндекс и `CALENDAR_SECRET_KEY` туда не передаются. Секрет связи общий у Worker/моста, хранится в исключённом `.env` и secret bindings/env. По умолчанию GigaChat не выбран.

`src/gigachat-relay.mjs`: фиксированный HTTPS-путь на vercel.app/netlify.app, HMAC-SHA256 по методу/пути, времени, дедлайну, UUID резерва и SHA-256 точного тела. Никаких Giga access tokens в Worker. Тело не более 110 KB, нет перенаправлений, максимум 12 секунд запроса.

`src/gigachat-bridge.mjs`: проверяет подпись, срок и ограничения до отправки данных. Допустимы только `GigaChat-3-Ultra`, до 900 выходных токенов, утверждённые схемы функций BOB без встроенных инструментов и два текстовых сообщения. Другие модели, дополнительные поля/контекст, изменённая подпись и старые запросы блокируются.

Перед OAuth/генерацией мост обращается к фиксированному `/providers/gigachat/claim` текущего Worker. Тот аутентифицирует отдельным секретом только эту операцию. ControlObject атомарно проверяет свежий незакрытый резерв GigaChat, активность/допуск участника, объём, и сохраняет однократный claim. Он переживает перезапуск и работает между разными экземплярами serverless-функции; повтор не вызывает модель. Claim не создаёт резерв и не позволяет менять дела. При потере ответа резерв консервативно списывается.

Node применяет официальный CA только к фиксированным GigaChat-адресам с проверкой TLS. OAuth/access token остаются в Node, с refresh и одним повтором после 401. Ответы ошибок не отражают тела провайдера или ключи. Код не пишет запросы/ответы в логи; стандартные журналы платформы и её условия — отдельная область проверки при публикации.

## Личный режим

При `GIGACHAT_PUBLIC_USE_CONFIRMED!=true` выбор GigaChat доступен **только владельцу** `TELEGRAM_OWNER_ID`, если остальные технические/free/quality gates выполнены. Новые публичные пользователи по-прежнему допускаются через /start и пользуются Cloudflare. Для общего GigaChat недостаточно желания владельца: необходимо выяснить применимость личного Freemium к такому использованию.

Активация требует relay URL/секрета, `GIGACHAT_ENABLED=true`, `GIGACHAT_FREE_CONFIRMED=true`, `GIGACHAT_TRANSPORT_VERIFIED=true`, `GIGACHAT_EVALUATED=true` и положительного `GIGACHAT_TOKEN_CAP` не выше остатка Ultra (максимум 50 млн). Практический консервативный начальный cap — 49,9 млн, оставляя запас на разрешённые опыты вне производственного счётчика. Кнопка согласия в /providers называет фактический хостинг (Vercel/Netlify) и GigaChat; автоматического переключения пользователей нет.

## Пакет публикации

`node scripts/build-gigachat-relay.mjs --ca work/gigachat-root.pem` собирает `work/gigachat-relay-release/`: 11 файлов и manifest, Node 24, функция `/api/gigachat`, timeout 15 с, без внешних npm-зависимостей. Явный allowlist копирует только необходимые исходники и проверенный публичный CA. Файлы .env/базы/Beads/другие ключи не копируются; неожиданные файлы в каталоге сборки останавливают сборку. Fingerprint CA проверяется. `deploy/gigachat-relay/api/gigachat.mjs` — шаблон точки входа, напрямую из папки исходников не запускается.

На выбранном Node-хостинге нужны только `GIGACHAT_AUTH_KEY` и `GIGACHAT_RELAY_SECRET`. На Worker — `GIGACHAT_RELAY_URL`, тот же `GIGACHAT_RELAY_SECRET` и управляющие флаги/cap. `deploy.mjs` не отправляет GigaChat Authorization key в Worker. Установка новых секретов/публикация выполняются после проверки реального Hobby-плана. Старый CF deploy-токен истёк 6 ноября; будущая публикация Worker требует отдельно разрешённого актуального доступа, чужие ключи/истёкший токен не подменяются молча.

## Проверка нового хостинга

`scripts/check-gigachat-relay-live.mjs --run` использует только фиксированную вымышленную задачу без срока, одну известную функцию, не исполняет предложение и не обращается к Telegram/пользовательским делам. Локальный постоянный журнал ограничивает весь опыт двумя попытками и 10 000 токенов. Перед сетью вычисляется консервативная верхняя граница; ограниченные admin endpoints дополнительно сохраняют максимум двух резервов суммарно до 10 000 в ControlObject. Это не сбрасывается перезапуском или публикацией.

`/admin/providers/gigachat/probe/reserve` и `/settle` доступны только с существующим ADMIN_SECRET, тело не более 256 байт. Браузерные запросы участника не могут получить такие резервы. Проверки нового маршрута ещё не запускались. Лимит прежнего Ultra-пилота 18 вызовов исчерпан; они не смешиваются с отдельно разрешённой проверкой хостинга.

В тестовом Worker ключ GigaChat отсутствует: цепочка идёт через подписанный Node bridge → callback-claim настоящей SQLite → подменённый Giga API → проверка действия → ответ. ### Пакет Netlify Free

`node scripts/build-gigachat-relay.mjs --platform netlify --ca work/gigachat-root.pem` собирает отдельный `work/gigachat-netlify-release/`, тоже 11 файлов без секретов. ESM-функция экспортирует Web Request → Response и `config.path=/api/gigachat`; `netlify.toml` задаёт functions/public, esbuild и Node24. Публичный каталог содержит только нейтральный index, исходники/ключи не публикуются статикой. Runtime Node24 подтверждён [официальной конфигурацией](https://docs.netlify.com/build/functions/configuration/). Обе собранные точки входа загружены локальным Node: health200 без генерации, неавторизованный POST403. Это не подтверждение реального аккаунта/сети Netlify.
